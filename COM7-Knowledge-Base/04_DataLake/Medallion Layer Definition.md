## หลักตัดสินใจข้อเดียวที่ใช้ตลอดทั้งเอกสาร

> **ชั้นล่างตอบคำถามว่า "ต้นทางส่งอะไรมา" · ชั้นบนตอบว่า "ธุรกิจหมายถึงอะไร"**

ทุกครั้งที่ไม่แน่ใจว่างานไหนควรอยู่ชั้นไหน ให้ถามว่า
**ถ้าทำขั้นนี้แล้ว ยังย้อนกลับไปเทียบกับต้นทางได้ไหม** — ถ้าไม่ได้ แปลว่าลงชั้นต่ำเกินไป

## เส้นแบ่งที่ชัดที่สุด — BU รวมกันเมื่อไหร่

```
Raw      แยกถังตามระบบ    ข้างในแยก BU
Bronze   แยกโฟลเดอร์ BU    + กอง master แยกต่างหาก      Iceberg
Silver   ยังแยก BU         คงโครงตารางเดิม  แค่ล้างแล้ว
Gold     รวม BU แล้ว       join ข้ามตาราง  พร้อมใช้ทันที
```

**สามชั้นล่างยังตอบได้ว่าแถวนี้เป็นของบริษัทไหน ตารางไหนในระบบต้นทาง**
พอถึง Gold จึงกลายเป็นมุมมองธุรกิจที่ไม่สนใจว่าข้อมูลมาจากระบบใด

# 🔴 สามจุดที่ย้ายจากร่างเดิม

ร่างเดิมวางงานไว้ผิดชั้น 3 จุด ซึ่งจะทำให้ Glue Job ทำงานเกินหน้าที่ตามที่ทีมกังวลไว้จริง ๆ

| งาน | ร่างเดิม | ควรเป็น | เหตุผล |
|---|---|---|---|
| **แปลงเป็น Parquet / Iceberg** | Bronze → Silver | **Raw → Bronze** | ถ้า Bronze ยังเป็น csv/json จะ query ไม่ได้ ต้องอ่านทั้งไฟล์ทุกครั้ง · และโครงถังที่วางไว้ (prefix แรก = BU) แปลว่าตั้งใจให้เป็นตารางอยู่แล้ว |
| **Schema normalization · Column naming** | Raw → Bronze | **Bronze → Silver** | ขัดกับหลักที่เขียนไว้เองว่า *"รักษาข้อมูลต้นฉบับให้ใกล้เคียง Source มากที่สุด"* · ถ้า rename ตั้งแต่ Bronze จะเทียบกับต้นทางไม่ได้เวลา audit |
| **One-Hot Encoding** | Silver → Gold | **แยกออกจาก Gold** | Power BI ใช้คอลัมน์ 0/1 ไม่ได้ · เป็น feature ของ ML ควรอยู่ feature store แยก ไม่ปนกับตารางที่ธุรกิจอ่าน |

**Data type correction** อยู่ได้ทั้งสองที่ แต่แนะนำให้แยก

- **Raw → Bronze** แก้เฉพาะชนิดที่ผิดจนอ่านไม่ได้ (เช่น วันที่เป็นข้อความ `20260924`)
- **Bronze → Silver** แก้ชนิดตามความหมายธุรกิจ (เช่น `QTY` เป็น decimal, barcode ต้องเป็น string เสมอ)

# Raw — ไฟล์ดิบตามต้นทาง

## โครงถัง

**แยกถังตามระบบต้นทาง ข้างในแยกตาม BU** ตามที่ทีมวางไว้

```
s3://com7-raw-itec/     bu=com7/ table=fact_sales_itec/ dt=2026-09-24/
s3://com7-raw-fo/       bu=com7/ table=Transaction_FO/  dt=2026-09-24/
                        bu=dou7/ ...
                        bu=bnn/  ...
s3://com7-raw-k2/       bu=com7/ ...
s3://com7-raw-crm/
s3://com7-raw-files/    ไฟล์แชร์ · Excel · Google Sheet · รูปภาพ · json
s3://com7-raw-icare/    จาก S3 ของแผนก Innovation
```

แยกถังต่อระบบทำให้ตั้ง **สิทธิ์ · lifecycle · ต้นทุน** แยกกันได้ ซึ่งสำคัญเพราะแต่ละระบบมีเจ้าของคนละทีม

## ทำอะไร / ไม่ทำอะไร

| ✅ ทำ | 🚫 ไม่ทำ |
|---|---|
| เก็บไฟล์ตามที่ได้มา ไม่แตะเนื้อใน | แปลงชนิดข้อมูล |
| ตั้งชื่อ path ให้เป็นระเบียบ | เปลี่ยนชื่อคอลัมน์ |
| บันทึกว่าได้มาเมื่อไหร่ จากไหน | ตัดแถวซ้ำ |
| เก็บ checksum ไว้ตรวจ | กรองแถวทิ้ง |

**ห้าม query ตรงจากชั้นนี้ และห้ามให้ผู้ใช้ปลายทางเข้าถึง** — มีไว้เพื่อ replay เมื่อ logic ชั้นบนเปลี่ยน

## รูปภาพและ JSON

ทีมระบุว่า Raw จะมีรูปภาพและ json ด้วย — ทั้งสองอย่าง**ไม่ต้องขึ้นไป Bronze ในรูปเดิม**

| ชนิด | ทำอะไรต่อ |
|---|---|
| รูปภาพ | อยู่ที่ Raw · Bronze เก็บแค่ **เมตาดาตา** (path · ขนาด · วันที่ · ผูกกับ ItemId ตัวไหน) |
| JSON | แตกเป็นตารางที่ Bronze · เก็บ json ดิบไว้ที่ Raw เผื่อ schema เปลี่ยน |
| Excel / Google Sheet | แปลงเป็น csv ที่ Raw ก่อน แล้วค่อยเข้า Bronze |

⚠️ **Excel ทำลายบาร์โค้ด 13 หลักถาวร** — `4960999036595` กลายเป็น `4.961E+12` กู้ไม่ได้
ถ้าต้นทางเป็น Excel ต้องอ่านด้วย library ที่บังคับ dtype เป็น string ห้ามให้คนเปิดแล้วเซฟทับ

## Retention

เก็บ **อย่างน้อย 13 เดือน** แล้วย้ายไป Glacier — ต้องข้ามรอบปีได้เพื่อทำรายงานเทียบปี

# Quarantine — ของที่ไม่ผ่านด่าน

**ไม่ใช่ชั้นของ medallion** แต่เป็นถังข้างทางที่แยกออกจาก Raw

```
s3://com7-quarantine/   reason=malware/ ...
                        reason=pii/     ...
                        reason=schema/  ...
```

| เข้าเมื่อไหร่ | ทำต่อยังไง |
|---|---|
| GuardDuty พบมัลแวร์ | แจ้งทีมความปลอดภัยทันที |
| Macie พบ PII เกินเกณฑ์ | แจ้ง DPO · ตัดสินว่าปิดบังแล้วปล่อยผ่าน หรือทิ้ง |
| โครงสร้างไฟล์ผิดจนอ่านไม่ได้ | แจ้งเจ้าของระบบต้นทาง |

**เก็บ 30 วันแล้วลบอัตโนมัติ** · 🚫 ชั้นบนห้ามอ่านจากที่นี่ทุกกรณี

> ร่างเดิมวาดเส้น `Quarantine → Glacier` — **ไม่ควรทำ** เพราะเท่ากับเก็บไฟล์ติดเชื้อไว้ถาวร

# Raw → Bronze

## งานที่ทำ

```
1. สแกนมัลแวร์        GuardDuty Malware Protection for S3
2. สแกน PII           Macie          <- ร่างเดิมยังไม่มีข้อนี้
3. แปลงเป็น Parquet / Iceberg
4. แก้ชนิดที่ผิดจนอ่านไม่ได้เท่านั้น
5. ใส่คอลัมน์ระบบ      _ingested_at · _source_file · _bu
```

## โครง Bronze

**แยกโฟลเดอร์ตาม BU เป็นชั้นแรก และมีกอง master แยกต่างหาก** · จัดเป็น **Iceberg** แล้ว

```
s3://com7-bronze/bu=com7/src=fo/tbl=Transaction_FO/year=2026/month=09/
s3://com7-bronze/bu=dou7/src=fo/tbl=Transaction_FO/year=2026/month=09/
s3://com7-bronze/bu=com7/src=itec/tbl=fact_sales_itec/year=2026/month=09/

s3://com7-bronze/master/src=fo/tbl=tm_Item/
s3://com7-bronze/master/src=fo/tbl=tm_Warehouse/
s3://com7-bronze/master/src=fo/tbl=tm_FinDimValueSet/
s3://com7-bronze/master/src=itec/tbl=dim_item_itec/
```

### ทำไม master ต้องแยกจาก BU

ตาราง master **ไม่ได้แบ่งตาม BU แบบเดียวกับตารางธุรกรรม**

| ตาราง | สภาพ |
|---|---|
| `tm_FinDimValueSet` | 719,054 แถว · มี `CompanyName` ในตัว · **ไม่ควรแตกเป็นโฟลเดอร์ BU** |
| `tm_Item` | 394,158 แถว · คีย์คือ `(ItemId, SysCompanyId)` · แตกได้แต่เล็กมาก |
| `tm_Warehouse` | 3,690 แถว · เล็กเกินกว่าจะแตก |
| `dim_item_itec` | 218,661 แถว · **ไม่มี BU เลย** ITEC ไม่แบ่งบริษัท |

ถ้าบังคับแตกทุกตารางตาม BU จะได้ไฟล์จิ๋วจำนวนมาก ซึ่งทำให้ Athena ช้าลงอย่างชัดเจน

### ข้อดีของ Iceberg ที่ควรใช้ให้คุ้ม

| ความสามารถ | ใช้กับอะไร |
|---|---|
| `MERGE INTO` | ต้นทางแก้ย้อนหลัง — F&O มีรายการคีย์ย้อนไปปี 2005 จริง |
| Time travel | ตอบผู้ตรวจว่า *"ณ วันที่รายงานออก ข้อมูลหน้าตาแบบไหน"* |
| Schema evolution | ต้นทางเพิ่มคอลัมน์โดยไม่แจ้ง — เกิดบ่อย |
| Hidden partitioning | เปลี่ยนวิธีแบ่งพาร์ทิชันได้โดยไม่ต้องเขียนข้อมูลใหม่ |

⚠️ **ข้อควรระวังเรื่องการกระจาย** — `com7` คิดเป็น **91% ของ `Transaction_FO`** (251.6M จาก 276.1M แถว)
การแบ่ง prefix ตาม BU อย่างเดียวจะได้พาร์ทิชันใหญ่มากหนึ่งก้อน จึงต้องมี `year` / `month` ซ้อนเสมอ

| BU | แถวใน Transaction_FO | % |
|---|--:|--:|
| com7 | 251,653,202 | 91.14 |
| dou7 | 13,369,482 | 4.84 |
| bnn | 5,183,648 | 1.88 |
| อีก 18 BU | 5,913,531 | 2.14 |

## กฎเหล็กของ Bronze

**ชื่อคอลัมน์ต้องเหมือนต้นทางเป๊ะ** รวมถึงชื่อที่น่าเกลียด

```
[FO-ITEMNO]  [ITEC-ITEMNO]  [Ref.DocNum]  [Model/Series]  [Create Time]
```

ถ้า rename ตั้งแต่ Bronze เวลาผู้ตรวจถามว่า *"ตัวเลขนี้มาจากคอลัมน์ไหนในระบบ"* จะตอบไม่ได้

**append-only** — ไม่ update ไม่ delete · ถ้าต้นทางแก้ย้อนหลัง ให้เขียนแถวใหม่ทับด้วย Iceberg merge แล้วเก็บประวัติไว้

# Bronze → Silver

ชั้นนี้คือที่ที่**ความรู้เรื่องข้อมูลถูกเขียนเป็นโค้ด** — งานหนักที่สุดอยู่ตรงนี้

## 🔴 Silver ยังแยก BU และคงโครงตารางเดิม

```
s3://com7-silver/bu=com7/tbl=transaction_fo/year=2026/month=09/
s3://com7-silver/bu=dou7/tbl=transaction_fo/year=2026/month=09/
s3://com7-silver/bu=bnn/ tbl=transaction_fo/year=2026/month=09/

s3://com7-silver/master/tbl=dim_item/
s3://com7-silver/master/tbl=dim_warehouse/
s3://com7-silver/master/tbl=dim_vendor/
```

**1 ตารางต้นทาง = 1 ตาราง Silver** ไม่ยุบ ไม่รวม BU — เปลี่ยนแค่คุณภาพข้างใน

เหตุผลที่ทำแบบนี้ถูกต้อง

| ข้อดี | ทำไมสำคัญกับเรา |
|---|---|
| ตรวจย้อนได้ทีละ BU | `drph` ช้า 78 วัน · `drl` ตายไป 2 ปี — ถ้ารวมแล้วจะไม่เห็น |
| รันใหม่เฉพาะ BU ที่พัง | com7 คิดเป็น 91% ของแถว ไม่ต้องรันใหม่ทั้งหมดเพราะ bnn เสีย |
| สิทธิ์แยกตามบริษัท | แต่ละ BU เป็นคนละนิติบุคคล |
| เทียบกับต้นทางได้ตรง | ผู้ตรวจถามทีละบริษัท |

## งานที่ทำ

```
1. Column naming        ชื่อมาตรฐาน — แต่ยังเป็นตารางเดิม ไม่ยุบ
2. Data type correction ตามความหมายธุรกิจ
3. Deduplication        ด้วยคีย์ที่พิสูจน์แล้ว
4. Cleansing            แก้กับดักที่รู้แล้ว (ตารางข้างล่าง)
5. Null / Invalid       จัดการค่าว่างปลอม
6. Data validation      ตรวจแล้วโยนแถวเสียไป quarantine
7. PII masking          ตัด/ปิดบังตาม PDPA
8. สร้าง dimension       สินค้า · คลัง · ผู้ขาย · สาขา -> กอง master
```

🚫 **ไม่ทำที่ Silver** — union ข้าม BU · join ข้ามตาราง · aggregate · one-hot

## Dimension — อยู่ในกอง master ของ Silver

Dimension เป็นข้อยกเว้นของกฎ "ไม่ join ที่ Silver" เพราะมันคือ**ตาราง master ที่ต้องประกอบจากหลายตาราง**
แต่ยัง **ไม่ใช่การ join ข้าม BU หรือข้ามข้อเท็จจริงทางธุรกิจ** จึงอยู่ Silver ได้

| ตาราง | สร้างจาก | ประเด็น |
|---|---|---|
| `dim_item` | `tm_Item` + `dim_item_itec` + สะพานรหัส | **สะพาน `ITEC-ITEMNO` ↔ `FO-ITEMNO` ติด 100% ของแถว** · 93,468 คู่รหัส |
| `dim_warehouse` | `tm_Warehouse` | ต้องมี `(WarehouseId, CompanyCode)` คู่กันเสมอ · มี `InTransiteWarehouse` ด้วย |
| `dim_vendor` | `purchtable` + `vendtable` + `dirpartytable` | ⚠️ ชื่ออยู่ `dirpartytable` ไม่ใช่ `vendtable` |
| `dim_branch` | `dim_branch_itec` + `tm_Warehouse` | สาขา ITEC `4` `77` = คลัง FO `4` `77` |

### ⚠️ สะพาน ITEC ↔ F&O เป็นของข้ามระบบ ไม่ใช่ข้าม BU

`dim_item` ต้องรวมรหัสจากสองระบบเข้าด้วยกัน ซึ่งดูเหมือนขัดกับกฎ Silver
**แต่ไม่ขัด** เพราะมันคือการผูกรหัสที่ชี้ไปสินค้าชิ้นเดียวกัน ไม่ใช่การรวมยอดข้ามบริษัท

```sql
SELECT DISTINCT [ITEC-ITEMNO], [FO-ITEMNO], CompanyCode
FROM Transaction_FO        -- 93,468 คู่ · ผูก 1:1 ภายในบริษัทเดียวกัน
```

`CompanyCode` ยังติดอยู่ในตาราง — ยังรู้ว่าคู่รหัสนี้เป็นของบริษัทไหน

# Silver → Gold

## 🔴 Gold คือที่เดียวที่ BU มารวมกัน

```
s3://com7-gold/mart=inventory/tbl=fact_movement_daily/
s3://com7-gold/mart=sales/    tbl=fact_sales_daily/
s3://com7-gold/mart=vendor/   tbl=fact_inbound_by_vendor/
```

ไม่มี `bu=` ใน path อีกแล้ว — `BU` กลายเป็น**คอลัมน์ธรรมดา** ที่ผู้ใช้กรองเอง

## งานที่ทำ

```
1. Union ข้าม BU        รวม 21 บริษัทเป็นตารางเดียว  <- เกิดที่นี่เท่านั้น
2. Join หลาย dataset    fact + dimension + ข้ามระบบ
3. Aggregation          sum · avg · count ตามมิติที่ธุรกิจใช้
4. นิยามตัวเลขให้ตรงกัน  ทุกรายงานต้องได้เลขเดียวกัน
5. ตารางสรุปสำเร็จรูป    สำหรับ dashboard ที่ต้องเร็ว
```

### สิ่งที่ต้องเติมตอน union

| ต้องเติม | เพราะ |
|---|---|
| `BU` เป็นคอลัมน์ | หายไปจาก path แล้ว ต้องอยู่ในข้อมูล |
| `BU_Name` อ่านออก | `com7` -> COMSEVEN · `bnn` -> Adept · `dou7` -> Double7 |
| `data_as_of` | ความสดไม่เท่ากัน — `drph` ช้า 78 วัน |
| `source_system` | ITEC หรือ F&O — ตอบ audit ได้ |

## 🔴 เรื่องที่ต้องตัดสินใจที่ Gold — ไม่ใช่ที่ Silver

### ① หมวดสินค้าต้องใช้ฉบับของทีมข้อมูล

หมวดจากระบบดิบ **ใช้ตรง ๆ ไม่ได้**

| ปัญหา | ขนาด |
|---|--:|
| `CategoryName` ชี้ไปหลาย `GroupCategoryName` | **345 จาก 487 หมวด (71%)** |
| `Common` อยู่ใต้กี่กลุ่ม | **67 กลุ่ม** |
| com7 ยัดของ demo ทุกชนิดลงกลุ่ม `iPhone` | แอร์ Xiaomi · หูฟัง Redmi ก็อยู่ในนั้น |
| ชื่อหมวดมีอักขระขยะ | `ฺฺBBP` 164,641 แถว |

→ ใช้ taxonomy ที่ทีมทำเอง **33 Main / 107 Sub** จาก [[ITEC Product Dimension]]

### ② การเคลื่อนไหวต้องแยกประเภท

**คลังกลางไม่ได้ขายให้ลูกค้า แต่โอนไปสาขา**

```
ITEC สาขา 4 (คลังกลาง)   Transfer-Out 8,424,259 แถว   ·   Sales 0 แถว
```

ถ้ารวมเป็นก้อนเดียวหรือนับแค่ Sales **ของที่ผ่านคลังจะหายไปเกือบ 90%**
→ ตารางที่ Gold ต้องมีคอลัมน์ `MovementType` แยก `PO ซื้อเข้า` / `SO ขาย` / `Transfer โอน`

### ③ การโอนมีสองรูปแบบ ต้องรวมให้เป็นนิยามเดียว

| BU | รูปแบบ | ขา |
|---|---|--:|
| `com7` | `Transfer` (refcat 6) | 2 ขา จบในวันเดียว |
| `dou7` `drph` `lor` `bnn` `drl` | `Transfer order shipment/receive` (21/22) | 4 ขา ผ่านคลังพัก คนละวัน |

Gold ต้องแปลงทั้งสองแบบให้เป็นเหตุการณ์เดียวกัน ไม่งั้นนับซ้ำ

### ④ ความสดของข้อมูลไม่เท่ากัน — ต้องแสดงให้ผู้ใช้เห็น

```
com7 · dou7 · bnn · lor    สดรายวัน
drph                       ช้า 78 วัน
gi04                       ช้า 106 วัน
drl                        ตายไป 2 ปี
```

ทุกตาราง Gold ควรมีคอลัมน์ `data_as_of` และ dashboard ต้องโชว์

## 🚫 สิ่งที่ไม่ควรอยู่ใน Gold

| งาน | ควรอยู่ที่ไหน |
|---|---|
| **One-Hot Encoding** | Feature store แยก — Power BI ใช้คอลัมน์ 0/1 ไม่ได้ |
| **Feature Engineering** สำหรับ ML | Feature store แยก |
| Normalize / Scale ตัวเลข | ในไปป์ไลน์ของ SageMaker |

> **แยก ML feature store ออกจาก Gold** — คนละผู้ใช้ คนละรอบการอัปเดต คนละนิยาม

# การแบ่ง Glue Job

ทีมกังวลว่า *"Glue ในบางขั้น อาจทำงานหลายอย่างเกินไป"* — ถูกต้อง แนวทางคือ **1 job = 1 หน้าที่ + 1 ขอบเขต**

| Job | ขอบเขต | ทำอะไร | ตารางเวลา |
|---|---|---|---|
| `raw_to_bronze_<src>` | 1 ระบบต้นทาง | แปลง Parquet · ใส่คอลัมน์ระบบ | ทุกครั้งที่มีไฟล์เข้า |
| `bronze_dedup_<tbl>` | 1 ตาราง | ตัดซ้ำด้วยคีย์ที่กำหนด | รายวัน |
| `bronze_to_silver_<tbl>` | 1 ตาราง | rename · แก้ชนิด · แก้กับดัก | รายวัน |
| `silver_dim_<name>` | 1 dimension | สร้าง dim_item / dim_vendor / ... | รายวัน |
| `silver_quality_<tbl>` | 1 ตาราง | ตรวจคุณภาพ · โยนแถวเสียไป quarantine | หลัง silver |
| `gold_union_<tbl>` | 1 ตาราง ทุก BU | **รวม 21 BU เป็นตารางเดียว** · เติม BU_Name · data_as_of | รายวัน |
| `gold_<mart>` | 1 data mart | join + สรุป | รายวัน / รายเดือน |

⚠️ **แยก `gold_union` ออกจาก `gold_<mart>`** — ถ้า BU ใด BU หนึ่งมาช้า (drph ช้า 78 วัน)
จะได้รู้ว่าปัญหาอยู่ที่ขั้น union ไม่ใช่ที่ logic ธุรกิจ

**อย่าเขียน job เดียวที่ทำ raw → gold รวด** — พังตรงไหนก็ต้องรันใหม่ทั้งหมด และหาสาเหตุไม่เจอ

## ทำไมต้องแยก dedup ออกจาก transform

`Transaction_FO` มี 276 ล้านแถว การตัดซ้ำต้องอ่านทั้งพาร์ทิชัน
ถ้ารวมกับ transform ในjob เดียว ทุกครั้งที่แก้ logic การทำความสะอาดจะต้องรัน dedup ใหม่ด้วย ทั้งที่ไม่จำเป็น
