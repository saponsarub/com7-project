# ICS (iCare Service)

> **ที่มา:** ประชุมสำรวจภาพรวมกับทีม **iCare** — **2026-09-11**
> แจ้งด้วยวาจา **ยังไม่มีเอกสารยืนยัน** · **data field survey จะตามมาอีกที**

**ICS = iCare Service** ระบบงานซ่อม/เคลมของศูนย์บริการ → แบรนด์แยกตามยี่ห้อที่ [[Smart Care Service]]

## ข้อมูลอยู่บน S3 ของแผนก Innovation แล้ว

**นี่คือข้อค้นพบที่สำคัญที่สุดของการประชุม**

| | |
|---|---|
| ระบบ | ICS (iCare Service) |
| ข้อมูลเก็บที่ | **S3 ของแผนก Innovation** |
| สิ่งที่ต้องทำต่อ | **ขอ connection / สิทธิ์เข้าถึงจากทีม Innovation** |

**ต่างจากทุกระบบที่สำรวจมา** — ITEC · K2 · ITOS · ICI ล้วนเป็นฐาน on-premise ที่ต้องผ่าน VPN และ DMS

```
ระบบอื่น    on-prem SQL Server ──VPN──► DMS ──► Bronze S3
ICS         S3 (Innovation) ─────────────────► Bronze S3     ← สั้นกว่ามาก
```

**ถ้าเป็น S3 ในองค์กรเดียวกัน อาจใช้แค่ bucket policy + cross-account role ไม่ต้อง DMS ไม่ต้อง VPN เลย**
`[อนุมาน — ยังไม่รู้ว่าเป็น AWS account เดียวกันไหม region ไหน รูปแบบไฟล์อะไร]`

**ต้องถามให้ครบก่อนดีใจ** — เป็น account เดียวกับ Data Lake หรือคนละ account · ไฟล์เป็น Parquet/CSV/JSON · เป็น export รายวันหรือ near-real-time · ใครเป็นเจ้าของ lifecycle · Innovation ยอมให้เข้าถึงตรงหรือต้องส่งต่อ

## GSX — รหัสของ "เคส" ไม่ใช่ของ "เครื่อง"

| | |
|---|---|
| GSX คือ | ระบบ **web-based ของ Apple** |
| รหัส GSX ได้มาเมื่อไหร่ | **ต้องเปิดเคสในระบบ Apple ก่อน ถึงจะได้เลขมา** |
| ติดมากับเครื่องไหม | **ไม่ · ไม่ได้มีพร้อมเครื่องแต่แรก** |
| เครื่องเดิมเปิดเคสใหม่ | **ได้เลข GSX ใหม่ทุกครั้ง** |
| เราเข้า database ได้ไหม | **ไม่ได้** |

### ความสัมพันธ์ที่ถูกต้อง

```
เครื่อง (Serial)  ──1:N──►  เคส  ──0:1──►  GSX id
     อยู่กับเครื่อง          Document Number     Apple ออกให้ตอนเปิดเคส
     ตลอดอายุ                                    ซ่อม 3 ครั้ง = GSX 3 เลข
```

**สามข้อที่ตามมาจากเรื่องนี้**

| # | ผล |
|---|---|
| 1 | **GSX ใช้แทน Serial ไม่ได้** — คนละระดับกัน · Serial ระบุเครื่อง · GSX ระบุครั้งที่ซ่อม |
| 2 | **GSX เป็น `0:1` ไม่ใช่ `1:1`** — เคสที่ยังไม่ได้ส่งเข้า Apple จะยังไม่มีเลข · **ต้องรองรับค่าว่าง** |
| 3 | **มีช่วงเวลาที่เคสมีอยู่แต่ยังไม่มี GSX** — ถ้า ingest ตอนนั้นแล้วไม่ ingest ซ้ำ จะได้เคสที่ GSX ว่างค้างถาวร |

**คีย์ของเคสคือ `Document Number` ไม่ใช่ GSX** — GSX มาทีหลังและอาจไม่มี

### ใช้ประโยชน์อะไรได้

**ข้อมูลฝั่ง Apple ดึงเข้ามาไม่ได้** สิ่งที่เรามีคือเลขที่ ICS บันทึกไว้เท่านั้น แต่ยังใช้ได้ 3 อย่าง

| ใช้ทำอะไร | อ่านจากอะไร |
|---|---|
| เคสไหน**ส่งเข้า Apple แล้ว** เคสไหนยัง | GSX ว่าง / ไม่ว่าง |
| เครื่องนี้**เข้าศูนย์ Apple มากี่ครั้ง** | นับ GSX ไม่ซ้ำต่อ Serial |
| **ระยะเวลาตั้งแต่เปิดเคสจนส่งเข้า Apple** | วันที่เปิดเคส เทียบวันที่ได้ GSX `[ถ้า ICS เก็บวันที่ได้ GSX ไว้]` |

**สถานะการซ่อมจริงฝั่ง Apple จะไม่อยู่ใน Data Lake** — ต้องอาศัยสถานะที่ ICS บันทึกเอง ซึ่งอาจไม่ตรงกับความจริง `[อนุมาน]`

### ต้องถามเพิ่ม

- หนึ่ง `Document Number` ได้ GSX **ได้มากกว่า 1 เลขไหม** (เช่น Apple ตีกลับแล้วเปิดใหม่)
- ICS เก็บ **วันที่ได้ GSX** แยกจากวันที่เปิดเคสไหม
- เคสที่ไม่ต้องส่ง Apple (ซ่อมจบที่ศูนย์เอง) มีสัดส่วนเท่าไหร่ — **ตัวนี้บอกว่า GSX ว่างเป็นเรื่องปกติแค่ไหน**

## กุญแจและรหัสในระบบ

### Document Number — กุญแจของเคส

**ถอดความหมายจากตัวเลขได้เลย**

```
Document Number
 └─ สาขา
 └─ ปี
 └─ เดือน
 └─ running number
```

| ข้อดี | ข้อควรระวัง |
|---|---|
| รู้สาขา/ปี/เดือน โดยไม่ต้อง join | **smart key** — ถ้าวันหน้าเปลี่ยนรูปแบบ ตัวเก่ากับตัวใหม่จะ parse ด้วยกฎเดียวกันไม่ได้ |
| เรียงลำดับเคสในสาขาได้จาก running number | running number **รีเซ็ตทุกเดือน** จึงไม่ unique ถ้าตัดส่วนหน้าออก |

**ต้องเก็บทั้งตัวเต็มและส่วนที่แตกแล้ว** — อย่าเก็บแค่ที่แตกแล้ว เพราะถ้ากฎ parse ผิดจะย้อนกลับไม่ได้

### Serial Number — **ซ้ำได้ ห้ามใช้เป็น primary key**

ใช้อ้างอิงเครื่อง Apple · **ทีมยืนยันเองว่าอาจซ้ำได้** จาก 2 สาเหตุ

| สาเหตุ | เกิดอะไร |
|---|---|
| เปิดเคสแล้ว **cancel แล้วเปิดใหม่** | เครื่องเดียวกัน 2 เคส |
| **เคลมมา 2 รอบ** | เครื่องเดียวกัน 2 เคส คนละเวลา |

**ตรงกับที่เราเจอเองฝั่ง ITEC** — [[ITEC - Query Cookbook]] R7 วัดได้ว่า ส.ค. 2026 มี 600,122 บรรทัดที่มี serial แต่ serial ไม่ซ้ำแค่ 136,077 → **ซ้ำ 4.4 เท่า**

> **สองฝั่งยืนยันตรงกันว่า serial ไม่ unique** — ใช้เป็นตัวเชื่อมได้ แต่ต้องเป็น **one-to-many เสมอ** และต้องมีเวลาเข้ามาช่วยตัด

### 'S' นำหน้า — กับดักตอน join กับ ITEC

| ระบบ | serial ที่เก็บ | มาจากไหน |
|---|---|---|
| ICS (iCare) | serial เครื่อง Apple | ตัวเครื่อง |
| ITEC | serial ที่**มี `S` นำหน้า** | **เลขหน้ากล่อง** |

**join ตรง ๆ จะไม่ match เลย** ต้อง normalize ก่อน — ตัด `S` นำหน้าออกแล้วค่อยเทียบ

**และต้องพิสูจน์ก่อนว่าเป็นเลขเดียวกันจริง** — เลขหน้ากล่องกับ serial ในเครื่อง **อาจเป็นคนละเลข** ไม่ใช่แค่ต่างกันที่ prefix `[ต้องทดสอบด้วยตัวอย่างจริง]`

### ตัวระบุเครื่องในเครือกระจัดกระจาย

| ระบบ | ใช้อะไรเป็นหลัก |
|---|---|
| ITEC | **IMEI** (`device emei id` ตอบว่ามี) · มี `SerialNo` ด้วย |
| ICS / iCare | **Serial** (Apple) |
| Smart Care | `Product serial no / เลข emii เครื่อง` |
| iCare Insurance | **IMEI** |

**สามระบบใช้ IMEI · หนึ่งระบบใช้ Serial** — ถ้าจะตามรอยวงจรชีวิตเครื่องให้ครบ ต้องมี **ตารางกลางที่ผูก IMEI ↔ Serial เข้าด้วยกัน** ซึ่งตอนนี้ยังไม่มีใครมี → [[System Inventory]] ระบุ "ทะเบียนอุปกรณ์ (ยังไม่มี)" เป็นช่องว่างอยู่แล้ว

### PHYID — สะพานที่คนเดินเอง

**ปัจจุบันเปิดเคสใน iCare แล้ว ต้องไปเปิดเคสใน ITEC เองอีกรอบ โดยใช้ PHYID**

```
iCare เปิดเคส ──(คนพิมพ์ซ้ำ)──► ITEC เปิดเคส
                  PHYID
```

**ผลต่อคุณภาพข้อมูล** — สะพานที่คนทำมือย่อมมี**เคสที่ลืมเปิดฝั่ง ITEC · พิมพ์ PHYID ผิด · เปิดช้ากว่าจริง** จึงต้องคาดไว้ว่า **การจับคู่ ICS ↔ ITEC จะไม่ครบ 100% แน่นอน** และตัวเลขที่ขาดคือความผิดพลาดของกระบวนการ ไม่ใช่ของข้อมูล

> `PHYID` ยังไม่ปรากฏใน [[ITEC - Data Dictionary]] — **ต้องถามว่าตรงกับฟิลด์ไหน**

## Repair Type มี 2 แบบ

| แบบ | หมายถึง |
|---|---|
| **Website** | ลูกค้าแจ้งผ่านเว็บ |
| **Walk-in** | ลูกค้าเดินเข้าสาขา |

ตรงกับฟิลด์ `ช่องทางที่แจ้ง claim: สาขา/หน้าร้าน` ในแบบสำรวจ [[Smart Care Service]]

**มีค่ากับการวิเคราะห์** — สองช่องทางนี้น่าจะมีคุณภาพข้อมูลลูกค้าต่างกันมาก เพราะ walk-in มีการอ่านบัตร (ดูหัวข้อถัดไป) ส่วน website ไม่มี `[อนุมาน]`

## อ่านบัตรประชาชนด้วย card reader

**หน้าร้านใช้ card reader อ่านบัตร ได้มา 4 อย่าง**

```
ชื่อ · เบอร์โทร · อีเมล · รหัสบัตร
```

**นี่คือข้อมูลระดับ SSOT** — เหตุผลเดียวกับ [[iCare Insurance (ICI)]]

| ทำไมมีค่ามาก | |
|---|---|
| **ได้เลขบัตรประชาชน** | กุญแจ dedupe อันดับ 1 ตาม [[Decisions]] D-08 |
| **อ่านจากบัตรจริง ไม่ได้พิมพ์** | คุณภาพสูงกว่าข้อมูลที่พนักงานพิมพ์เอง — ไม่มีพิมพ์ผิด |
| ได้ทั้ง 3 กุญแจในครั้งเดียว | เลขบัตร + เบอร์ + อีเมล |

**แต่ต้องถามต่อ** — card reader อ่านได้ทุกเคสหรือเฉพาะ walk-in · ข้อมูลที่อ่านถูกบันทึกลงฐานหรือใช้แค่กรอกฟอร์ม · **มี consent ตอนอ่านบัตรไหม** → [[Consent & PDPA]]

**เลขบัตรประชาชนเป็น PII ระดับสูงสุด** — ต้อง tokenize ก่อนเข้า Data Lake เหมือน `customer_master.citizen_no` ของ CRM

## สิทธิ์การเห็นข้อมูลผูกกับสาขา

> **ปกติสาขาไหนจะเห็นข้อมูลลูกค้าแค่สาขาตัวเอง ยกเว้นส่วนกลาง**

**นี่คือกับดักที่ทำให้ได้ข้อมูลไม่ครบโดยไม่รู้ตัว**

ถ้า connection ที่ขอมาถูกผูกกับสิทธิ์ระดับสาขา **จะดึงได้แค่บางส่วนและดูเหมือนสำเร็จ** ไม่มี error อะไรฟ้อง

**ต้องระบุให้ชัดตอนขอ** — ขอสิทธิ์ระดับ**ส่วนกลาง** ที่เห็นทุกสาขา และ**ตรวจยอดข้ามสาขาหลังดึงครั้งแรก** ว่าจำนวนสาขาที่พบตรงกับที่ควรจะมี

## Pain point ของทีม = โจทย์เดียวกับเรา

> **ทีม iCare อยากให้เชื่อม API กับ ITEC โดยตรง** เพราะตอนนี้ต้องเปิดเคสสองระบบด้วยมือ

**ความต้องการของเขากับของเราตรงกันพอดี**

| ฝั่ง iCare อยากได้ | ฝั่งข้อมูลได้อะไรตาม |
|---|---|
| ไม่ต้องพิมพ์ซ้ำสองระบบ | **การจับคู่ ICS ↔ ITEC กลายเป็นของระบบ ไม่ใช่ของคน** |
| เคสตรงกันทันที | ข้อมูลครบ ไม่มีเคสตกหล่น |
| ลดพิมพ์ผิด | **join ได้จริงโดยไม่ต้องทำ fuzzy matching** |

**เป็นข้อเสนอที่ควรผลักดันร่วมกัน** — ไม่ใช่งานของทีมข้อมูลโดยตรง แต่ถ้าเกิดขึ้นจะแก้ปัญหาคุณภาพข้อมูลให้เราฟรี ๆ

## สิ่งที่ต้องทำต่อ

| # | ทำอะไร | กับใคร |
|---|---|---|
| 1 | **ขอ connection / สิทธิ์เข้าถึง S3 ของ ICS** | ทีม Innovation |
| 2 | ระบุว่าต้องการสิทธิ์**ระดับส่วนกลาง** ไม่ใช่ระดับสาขา | ทีม Innovation / iCare |

| 5 | ถามว่า `PHYID` ตรงกับฟิลด์ไหนใน ITEC | ITEC |

## คำถามที่ยังไม่มีคำตอบ

- S3 ของ Innovation อยู่ **AWS account เดียวกับ Data Lake ไหม** · region ไหน
- ไฟล์รูปแบบอะไร · export รอบละเท่าไหร่ · เก็บย้อนหลังแค่ไหน
- ICS ใช้ฐานเดียวกับ **Smart Care** หรือแยก → [[Smart Care Service]]
- `Document Number` รูปแบบจริงเป็นอย่างไร กี่หลัก
- `PHYID` คือฟิลด์อะไร ตรงกับอะไรใน ITEC
- ข้อมูลจาก card reader ถูกบันทึกลงฐานหรือใช้แค่กรอกฟอร์ม
- ความคุ้มครองสินค้าที่ศูนย์ซ่อม เป็นตัวเดียวกับกรมธรรม์ [[iCare Insurance (ICI)]] หรือไม่
