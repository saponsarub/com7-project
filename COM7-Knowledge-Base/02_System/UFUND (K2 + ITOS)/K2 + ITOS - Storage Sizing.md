# K2 + ITOS — ขนาดข้อมูลสำหรับย้ายไป S3

วัดเมื่อ 2026-10-15 · K2 = ฐาน `HPCOM7` · ITOS = ตารางที่เห็นผ่าน linked server `ILOAN_DATASOURCE` (external table 281 ตัว + ตารางในฐานเอง 296 ตัว)
วิธีวัด → หัวข้อ 5 · ไฟล์ผลละเอียดอยู่ใน scratchpad ของ session (ไม่ได้เก็บใน repo เพราะมีชื่อตาราง/จำนวนแถวเท่านั้น ไม่มีข้อมูลลูกค้า — ถ้าต้องการให้ย้ายมาเก็บได้)

### 2.2 ไฟล์ที่ฝังในตาราง — 7.18 TB

เก็บแบบ K2 SmartForms: `<file><name>ชื่อไฟล์</name><content>base64…</content></file>` ในคอลัมน์ `nvarchar(max)`

| ตาราง | LOB | คอลัมน์ตัวอย่าง |
|---|---:|---|
| `IMAGE_FILE` | 1.9 TB | `CARD_CODE_FILE` · `FACE_PERSON` · `SLIP_FILE` · `BANK_STATE_FILE` · `PRODUCT_SERIAL` · `CUSTOMER_DELIVER` |
| `PROSPECT_CUSTOMER` | 1.5 TB | `IDCARD_FILE` · `FACE_FILE` · `BANK_STATE_FILE*` |
| `PDF_FORM` | 1.3 TB | `PDF_NAME` (PDF ใบแจ้งหนี้/สัญญา ทั้งไฟล์) |
| `PERSON` | 1.3 TB | `CARD_CODE_FILE` · `FACE_PERSON` · `CONSENT_FILE` · `STATEMENT_FILE` · `SLIP_FILE` |
| `PRODUCT` | 0.9 TB | `IMAGE_DELIVER` · `SIGNATURE_CONFIRM` |

- **รูปบัตรประชาชน · รูปใบหน้า · statement ธนาคาร** = ข้อมูลส่วนบุคคลอ่อนไหว (รูปใบหน้า = ข้อมูลชีวภาพ) → **ไม่ควรเข้า data lake** · ถ้าต้องเก็บตามกฎหมาย/สัญญา ให้แยกเป็น bucket เอกสารที่จำกัดสิทธิ์ ไม่ใช่ชั้น Raw/Bronze → [[Consent & PDPA]]
- แยกเป็นไฟล์จริงจะเล็กลง ~2.7 เท่า (base64 ใหญ่กว่าไฟล์ 4/3 · `nvarchar` ใช้ 2 byte/อักษร) → 7.18 TB ≈ **2.7 TB**
- **ตอนตั้ง DMS ต้องตัดคอลัมน์เหล่านี้ออก** (table mapping `remove-column`) — ไม่งั้น full load ต้องอ่าน 7 TB จากเครื่องจริง

## 3. ITOS (ผ่าน ILOAN_DATASOURCE)

ตาราง ITOS จริง (iLoan: ใบคำขอ · สัญญา · รับชำระ · ลูกค้า · ติดตามหนี้) อยู่หลัง **external table 281 ตัว** → วัดพื้นที่ใน SQL Server ตรงไม่ได้ จึง **นับแถวทุกตาราง + สุ่มวัดตารางที่มี ≥ 50,000 แถว (75 ตาราง)** · ขนาด SQL ประมาณจาก CSV ÷ 0.91 (อัตราของ K2) `[ประมาณ]`

## 4. ปรับชนิดข้อมูล (datatype) ช่วยลดขนาดไหม

ทดสอบกับ 59 ตาราง K2: ปรับ **ตัดช่องว่างท้าย `nchar` · `'NULL'` เป็น null จริง · ตัวเลขที่เก็บเป็นข้อความ → ตัวเลข · ข้อความวันที่ → timestamp · float ที่เป็นจำนวนเต็ม → int · ลดขนาด int**

| รูปแบบ | ขนาดเทียบ SQL Server data |
|---|---:|
| CSV (แบบที่ DMS เขียนเป็นค่าเริ่มต้น) | 91% |
| Parquet + zstd · ชนิดข้อมูลตามต้นทาง | **11.2%** |
| Parquet + zstd · ปรับชนิดข้อมูลแล้ว | 12.3% |

**ผล: ปรับชนิดข้อมูลแล้วไฟล์ Parquet ไม่เล็กลง (ใหญ่ขึ้น ~10%)** — Parquet บีบอัดข้อความที่ซ้ำกันได้ดีอยู่แล้ว (dictionary encoding) การแปลงเป็นตัวเลข/วันที่จึงไม่ช่วยเรื่องขนาด
**ตัวที่ลดขนาดจริงคือ** (1) ไม่เอาไฟล์ฝัง (7 TB) (2) ไม่เอา backup/สำเนาซ้ำ/log (3) เปลี่ยนจาก SQL/CSV เป็น Parquet (~9 เท่า)
**แต่ยังควรปรับชนิดข้อมูลตอนทำ Silver** เพราะได้ความถูกต้องและความเร็ว ไม่ใช่ขนาด:
- เงินใน K2 เป็น `float` (เช่น `REPAYMENT.PAY_AMT`) → `decimal(18,2)` กันเศษทศนิยมเพี้ยนตอนรวมยอด
- วันที่ที่เก็บเป็นข้อความ → `date`/`timestamp` ให้ filter/partition ได้
- `nchar` มีช่องว่างเติมท้าย → ตัดก่อน join

## 5. วิธีวัด และข้อจำกัด

| ส่วน | วิธี |
|---|---|
| ขนาด SQL Server ของ K2 | `sys.allocation_units` แยก in-row / LOB / index (ไม่มีสิทธิ์ `VIEW DATABASE STATE` แต่ query นี้ใช้ได้) |
| ขนาด Parquet K2 | ดึง 50,000 แถวแรกของ 60 ตาราง (ครอบคลุม 99.8% ของข้อมูลธุรกิจ) ไม่รวมคอลัมน์ไฟล์ → เขียน Parquet zstd **ใน memory** → byte/แถว × จำนวนแถวทั้งหมด · ตารางที่ไม่ได้สุ่มใช้อัตราส่วนของกลุ่ม |
| ITOS | `COUNT_BIG(*)` ทุก external table · สุ่ม 30,000 แถวของตาราง ≥ 50,000 แถว · ตารางเล็กใช้ 40 B/แถว · ไม่ดึงเนื้อข้อมูลของตารางรหัสผ่าน/ผู้ใช้ |
| ไฟล์ฝัง K2 → ไฟล์จริง | LOB × 0.375 (base64 4/3 · UTF-16 2 byte) |

- ตัวอย่างเป็น **แถวต่อเนื่องช่วงต้นตาราง** — ข้อมูลเก่าอาจบีบอัดได้ต่างจากข้อมูลใหม่ ตัวเลข Parquet คลาดได้ราว ±30% `[อนุมาน]`
- ขนาด SQL ของ ITOS เป็น**ค่าประมาณ** (ไม่มีสิทธิ์ดูพื้นที่ฐานจริง `ILOAN_COLLECTION` / cash receive)
- การจัดกลุ่มตารางใช้ชื่อตาราง (เช่น `BACKUP` · `_READ` · `LOG`) — ควรให้เจ้าของระบบยืนยันว่า `TTP_*` · `Report_*` · `R_APP_SCHEDULE` ไม่ต้องใช้จริง
- ไม่ได้ข้อมูลส่วนบุคคลออกมานอก memory — ผลที่บันทึกมีแค่ชื่อตาราง จำนวนแถว ขนาด
